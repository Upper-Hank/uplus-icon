## 系统目标

Uplus Icon 是一套面向产品界面的线性图标系统。它需要同时保证视觉一致、资产可追溯、公共 API 稳定，以及逐图标消费时的包体效率。

- **必须**以 `packages/icons/raw/<name>.svg` 中负责人确认的单一 `24×24` Canonical SVG 作为 v1 唯一视觉真源。
- **必须**把分类、标签、别名和发布状态维护在 `packages/icons/metadata`，不得写进 SVG。
- **应该**优先采用简单、可复现、可以由构建验证的工程方案。
- **可以**在出现真实消费者需求后增加新的框架包，但所有包必须消费同一份 Core Definition。
- **禁止**在展示网站、React 包或 Web 包中维护第二份手工复制的图形。

## 规则等级

| 等级 | 含义 |
| --- | --- |
| **必须** | 不满足时资产或代码不能合入。 |
| **应该** | 默认遵守；偏离时需要明确、可复核的理由。 |
| **可以** | 在不破坏其他规则时允许采用。 |
| **禁止** | 任何情况下都不能进入正式真源或公共产物。 |

## 三类事实来源

### 视觉真源

正式 SVG 决定路径、坐标、描边、填充、圆角和节点顺序。v1 每个图标只有一份 `24×24` Canonical SVG，不建立光学尺寸矩阵。生成器可以读取和编译这些文件，但不能写回或推导其他资产。

### 语义真源

元数据决定名称、标题、分类、标签、别名、弃用状态和版本信息。展示平台的搜索与分组必须来自这些数据。

### 生成产物

`packages/*/src/generated` 和 `dist` 都是可重复生成的结果，不是人工维护入口。

- **必须**通过修改真源或生成器改变生成结果。
- **禁止**为了通过测试而直接修补 generated 或 dist。

## 原始 SVG 保护

- **必须**由负责人明确提供或批准新增、替换和视觉修复。
- **必须**在发现不一致或无法构建时报告具体文件和原因。
- **禁止**自动优化、格式化、重绘或覆盖正式 SVG。
- **禁止**根据截图、其他图标库或主观判断生成正式资产。
- **禁止**让代码生成、测试或文档工具反向写入 raw 目录。

## 数据流

```text
approved SVG + metadata
  → validation
  → @uplus-icon/core
  → @uplus-icon/react / @uplus-icon/web
  → documentation / product code
```

每一层只能承担自己的职责：真源描述事实，生成器验证并编译，运行时提供消费能力，展示网站负责检索和说明。
